# 流式：为什么回答是<br/>一个字一个字蹦出来的

<Lede>这一课有一个**不会报错的 bug**。它安静地丢掉大部分内容，退出码还是 0。生产环境里最难查的就是这种。</Lede>

## 为什么这一课值得花时间

两个理由，一个关于产品，一个关于工程。

**产品上**：流式是所有 AI 产品的体验基础。同样一段话，等 3 秒一次性出现，
和立刻开始一个字一个字往外蹦 —— 用户感知到的速度差了好几倍。
你做过前端性能优化，这个道理你比我熟：**感知延迟 ≠ 实际延迟**。

**工程上**：流式的数据格式叫 **SSE**（Server-Sent Events）。
它的解析有一个**静默失败模式** —— 写错了不报错，只是丢数据。
今天你会亲眼看到它怎么坏。

### 和上一课对比，三个变化

| | 非流式（第 0001 课） | 流式（现在） |
| --- | --- | --- |
| `object` | `chat.completion` | **`chat.completion.chunk`** |
| 内容字段 | `choices[0].message` | **`choices[0].delta`** |
| `usage` | 一个对象 | **每个 chunk 都有，但只有最后一个是非 null** |

`delta` 是「增量」的意思 —— 每个 chunk 只带**这一小段**，不是完整内容。
所以你要自己把它们**拼起来**。

<Callout kind="warn" title="两个只看一遍就会忘的细节">

**① 第一个 chunk 的 `content` 是空字符串**，只带 `role`。
所以拼的时候要过滤掉空值，否则会多出看不见的字符。

**② `stream_options.include_usage` 不开的话，整个流里拿不到任何 token 统计。**
注意它**没有单独的 usage-only chunk** —— 统计是搭在最后一个内容 chunk 上的。

</Callout>

## 这叫 SSE，三条规则

SSE 是个很简单的协议，你只需要记三条：

1. 每条事件以 **`data: `** 开头
2. 事件之间用**一个空行**（也就是 `\n\n`）分隔
3. 流以 **`data: [DONE]`** 结束

就这么简单。真正的难点在**第 2 条**。

## 为什么它会静默丢数据

根源是一句很容易想当然的假设：

> 「每次 `read()` 拿到的就是一条完整的事件」

**这句话是错的。** TCP 给你的是**字节流**，不是**消息流**。
它不保证任何边界对齐 —— 一次 `read()` 可能给你：

- 半条事件
- 一条半事件
- 三条事件
- 甚至一个**多字节 UTF-8 字符的前两个字节**

那份反面教材就是这么写的：

```js
for await (const piece of res.body) {
  const s = decoder.decode(piece, { stream: true })
  for (const part of s.split('\n\n')) {   // ★ 这里就是 bug
    // 假设 part 是一条完整事件
  }
}
```

`split('\n\n')` 在**半条事件**上会切出一段残缺的 JSON，`JSON.parse` 抛错，
被 `catch` 吞掉 —— 数据就没了。

## 正确的写法：一个跨 read 的缓冲区

**先想清楚 buffer 是干什么的。**

它的职责只有一个：**暂存「还不能确定」的东西。**

一个事件什么时候算「确定完整」？**当它后面出现了 `\n\n` 的时候。**

所以每一轮 `read()` 之后，buffer 里其实分成两段：

```text
buffer = "……最后一个 ⏎⏎ 之前的内容……" + "……最后一个 ⏎⏎ 之后的内容……"
          └─── 后面有分隔符 → 确定完整 ───┘ └─── 还没等到分隔符 → 不确定 ───┘
```

**前半段切走处理，后半段留着等下一片。** 就这一件事。

### 走一遍真实的字节

上面演示的那三片拼起来，正好是服务端发出的完整流。
注意看第 2 步 —— **`da` 和 `ta` 拼回了 `data`**：

| 第几次 read | 拿到 | 拼接后 buffer | 切走 | 留回 |
| --- | --- | --- | --- | --- |
| 1 | `data: A⏎⏎da` | `data: A⏎⏎da` | `A` | `da` |
| 2 | `ta: BBB⏎⏎data: C` | `data: BBB⏎⏎data: C` | `BBB` | `data: C` |
| 3 | `C⏎⏎data: [DONE]⏎⏎` | `data: CC⏎⏎data: [DONE]⏎⏎` | `CC`、`[DONE]` | （空） |

**单词 `data` 本身都被切成了两半。** 这就是为什么你不能假设任何边界。

### 三种做法的后果

| 做法 | 后果 |
| --- | --- |
| 每轮把 buffer 整个清空 | 把「还不确定」的那段一起丢了 → **静默丢数据**（第 1 步的 `da` 就没了） |
| 处理过的也一直留在 buffer 里 | buffer 无限增长；而且下一轮你会把处理过的事件**再处理一遍**（重复输出） |
| **切走完整的，留下残片** | 不丢、不重复、还能立刻显示 ✅ |

### 代码

```ts
let buffer = ''

for await (const piece of res.body) {
  // ① 追加到缓冲区（stream: true 让 TextDecoder 自己处理跨包的 UTF-8）
  buffer += decoder.decode(piece, { stream: true })

  // ② 按分隔符切成若干段，最后一段可能不完整
  const parts = buffer.split('\n\n')

  // ③ ★ 关键：最后一段留着，其余才是完整事件
  buffer = parts.pop() ?? ''

  for (const part of parts) {
    if (!part.startsWith('data: ')) continue
    const payload = part.slice(6)
    if (payload === '[DONE]') continue
    const json = JSON.parse(payload) // 到这里才保证是完整 JSON
    // …
  }
}
```

#### 为什么 `parts.pop()` 就等于「留下残片」

`split('\n\n')` 会在**每一个** `\n\n` 处切开字符串。
切完之后，**数组的最后一个元素，正好就是「最后一个 `\n\n` 之后的内容」** —— 也就是残片。

`pop()` 把它取出来赋回 `buffer`，其余就是能确定完整的部分。

> 一句话记住：**`split` 负责切，`pop` 负责留。**

还有一处容易漏：`decoder.decode(piece, { stream: true })` 里的 **`{ stream: true }`**。
它会记住被切断的多字节字符，等下一段补齐 —— 少了它，中文会变乱码。
（这和缓冲区是**两个不同层面**的同一个问题：一个是字符被切断，一个是事件被切断。）
