# 取消：用户说停，<br/>你的代码要真的停下来

<Lede>第 0008 节让客户端「扛得住失败」。这一节处理另一种情况：请求没出错，只是用户不想等了。</Lede>

## 用户按了停止之后

流式界面里，几乎每个人都会按一次停止。原因很多：答案已经够了、答偏了、或者只是等得不耐烦。

如果代码不处理，会发生两种情况：

- **连接还开着**：你可能还在读流，也可能已经放弃了读但没关连接。前者浪费带宽，后者让服务端继续做无用功。
- **界面还在变**：如果停止按钮只改了 UI 状态、没有真的中止请求，后台会继续收数据，用户以为停了，其实还在花时间。

这一节讲怎么把「停」变成一个真正的动作。

## 实测：取消到底省下了什么

故障服务器有一个场景 `slowbody&ms=300`：每 300 毫秒吐一个字，共 10 个字。我们先完整跑一次，再在第 700 毫秒取消一次：

```text
完整跑完：用时 3015 ms，收到 10 个字符
700ms 时取消：用时 1005 ms，已收到 3 个字符，抛出 AbortError
→ 省下约 7 个字符的生成时间（按 300 ms/字 估算约 2100 ms）
```

三个结论：

1. **取消是立刻生效的**：700 ms 发起，1005 ms 抛错结束（含 300 ms 的 IO 延迟）。
2. **已经收到的内容是真的**：3 个字符已经拿到了，可以显示给用户。
3. **省下的是生成时间**：另外 7 个字不再等、不再读。

<Callout kind="note" title="字段在哪">

`signal.aborted` 是布尔，`signal.reason` 是错误对象；`e.name` 区分超时和取消，断流的底层原因在 `e.cause.message` 里。

完整的位置表在速查卡：**[失败与取消的字段](/reference/error-shapes)**。

</Callout>

## 原理：AbortController 做了什么，没做什么

你做的事只有两行：建一个 `AbortController`，把它的 `signal` 交给 `fetch`；要停的时候调用 `abort()`。

```ts
const c = new AbortController()

const res = await fetch(url, { signal: c.signal })

// 任何地方都可以调用它来中止——比如「停止」按钮
stopButton.addEventListener('click', () => c.abort())
```

`c.abort()` 之后，Node 侧会发生三件事：

- `fetch` 立刻以 `AbortError` 拒绝（如果还在等响应头）。
- 如果已经在读流，读流的 `for await` 也会抛出 `AbortError`。
- 底层连接被关闭。

这是 `probe:resilience` 实测到的：中途取消会「读到 639 字节后抛错 → AbortError(code=20)」。

<Callout kind="warn" title="它不能保证服务端停工">

`abort()` 关闭的是**你这边的连接**。服务端是不是立刻停止生成，我们无法确认，也没有测。

对我们有直接影响的一点是：**中途取消拿不到 `usage`**。`usage` 在最后一块事件里，取消发生在它之前，所以你不会有这次的 token 账单。要知道「取消到底花了多少钱」，只能在服务端日志里看。

</Callout>

## 原理：取消绝对不能重试

第 0008 节把错误分成三类，其中 `cancel` 是「不许重试」。

理由很直接：**用户要的是「停下来」，不是「再来一次」。** 你的客户端如果自动重试，用户会看到界面上又冒出来一批新字——这比一开始卡住更糟。

实测也证实了操作上做得到：`probe:resilience` 里「已 abort 的 signal 再发请求」那一段，一个已经 `abort()` 过的 signal 再发请求，**1 毫秒就抛错，请求根本没有发出去**。所以重试的循环里必须先判断「这个 signal 是不是已经取消了」，再谈要不要重试。

判断的依据就是错误名：`AbortError` 是取消，`TimeoutError` 是超时。第 0008 节那张表就是为这件事准备的。

## 原理：流到一半取消，已到的内容怎么办

这是**前端必须处理**的部分，也是很多人做错的地方。三种做法，只有一种是对的：

- ❌ **丢掉全部内容**：用户已经看了一半，突然清零，体验最差。
- ❌ **自动重试、重新开始**：前面的字会重复出现，而且用户的「停」被无视。
- ✅ **保留已到的内容，标记为「被中断」，不再追加**。

具体到代码，骨架是这样：

```ts
const c = new AbortController()
const res = await fetch(url, { signal: c.signal })

let text = ''
try {
  for await (const piece of res.body) {
    text += decoder.decode(piece, { stream: true })
    render(text)                       // 每收到一块就渲染，已到的内容不会丢
  }
} catch (e) {
  if (e.name === 'AbortError') {
    render(text + '（已停止生成）')      // 保留，标记中断，不重试
  } else {
    render(text + '（连接中断）')
    // 这里也**不要**自动重试：已经产生过输出，重试会拿到一份对不上的新回答
  }
}
```

界面上的表现是：保留已经渲染的文字，末尾加一句「已停止生成」，输入框恢复可用。第 5 章做流式界面时会把它做成组件。

## 原理：超时和取消要合成一个 signal

一个请求可能既要「5 秒没响应就放弃」，又要「用户随时可以停」。这是两个独立的触发源，要合并成一个：

```ts
const user = new AbortController()          // 用户点停止时调用
const signal = AbortSignal.any([
  user.signal,
  AbortSignal.timeout(5000),                // 超时
])
```

`AbortSignal.any` 会在**任意一个**触发时中止，并把那个触发源的错误名传出来。它在 Node 20 以上和主流浏览器的新版本里都有；运行环境更老的话得自己实现：监听两个 signal 的 `abort` 事件，谁先触发就用谁。

实测：

```text
any([用户取消, 超时])，用户先取消   ❌ AbortError
any([用户取消, 超时])，超时先生效   ❌ TimeoutError
```

所以你仍然可以用 `e.name` 区分「该重试」（超时）和「不该重试」（用户取消）。

## 原理：还有两种情况不能重试

除了用户取消，还有两种：

**① 已经吐出去内容了。** 一个流式请求已经发了 200 个字然后断了，这时候重试会拿到一份**新的**完整回答，和前面 200 个字对不上。正确做法是：把这次当作失败，保留已到的内容，让用户重来。这一条和第 0008 节的「重试」看起来是冲突的，但其实是一条更基本的规则在起作用。

<Callout kind="warn" title="重试的前提">

**重试只适用于「还没产生任何输出」的请求。**

一旦已经把内容交给了用户，重试就等于用一份新答案覆盖旧答案。要么不重试（保留 + 标记中断），要么重试后**明确告诉用户「重新生成了」**，绝不能悄悄替换。

</Callout>

**② 工具已经执行了。** 如果这一轮已经调用过「发邮件」这种有副作用的工具，重试会让它执行两次。这类操作要么做成幂等（带唯一 ID），要么不重试。

## 你的产出

取消不是新练习，它就是第 0008 节 `ex:client` 里 TODO 3 的一部分——`callWithRetry` 必须处理传进来的 `signal`。跑之前记得先在另一个终端启动故障服务器。

```bash
npm run ex:client
```

自检里有两项专门验这件事：

- `用户取消后不再重试`：用 `AbortSignal.any` 合成信号，用户取消后必须归为 `cancel`，且尝试次数不增加。
- `超时归类为 retry，并最终放弃`：超时归为 `retry`，但用完了 `maxAttempts` 就放弃。

能过这两项，说明你既没有把取消当超时，也没有把超时当取消。

## 第 2 章完成：你现在能教别人什么

这一章的两节讲的是同一件事的两面：**请求失败时，先判断它是哪一种，再决定做什么**。如果你能把下面六个问题讲清楚，就可以给别人讲这一章了。

1. **`fetch` 收到 500 会不会抛错？** 不会。它只在网络层失败时抛错，HTTP 状态要自己判断 `res.ok`。
2. **超时和用户取消，怎么区分？** 看错误名：`TimeoutError` 是超时（可重试），`AbortError` 是取消（绝不重试）。
3. **哪些错该重试？** 超时、429、5xx、连接断开。400/401/422 不该重试——同一份请求再发也是同样的错。
4. **重试之间要等多久？** 指数退避（200 → 400 → 800 ms）加随机抖动；429 有 `Retry-After` 就听它的；总共等待要有上限。
5. **重试有什么代价和前提？** 代价是延迟、并发占用、给已经过载的服务端加压；前提是这次操作**幂等**，并且**还没有产生任何输出**。
6. **用户按了停止之后，已收到的内容怎么办？** 保留、标记「已停止生成」、绝不自动重试。

如果这六条里有哪一条你只能背出结论、说不出原因，回去看对应的那一节。
