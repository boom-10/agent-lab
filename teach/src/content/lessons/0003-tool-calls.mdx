# 工具调用：从「会说话」<br/>到「能做事」

<Lede>前两节模型只能输出文本。这一节它第一次能<b>要求做事</b> —— Agent 真正的起点就在这里。</Lede>

## 为什么这一节是分水岭

前两节你做的所有事，本质都是「问一句话，拿一段文本」。

**工具调用改变了这个关系的性质**：模型不再只是回答你，它会说
「我需要调用 `get_weather`，参数是 `{"city":"杭州"}`」—— 然后**停下来等你执行**。

这个「停下来等你」是整个 Agent 的机制基础。后面所有的循环、规划、多智能体，
都建在它上面。

## 动手：让模型查天气

<Callout kind="do" title="复制粘贴">

```bash
cd ~/Desktop/Personal/agent-lab/lab
set -a; . ./.env; set +a

curl -s https://api.deepseek.com/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -d '{
    "model": "deepseek-flash",
    "messages": [{"role":"user","content":"杭州现在天气怎么样？"}],
    "thinking": {"type":"disabled"},
    "tools": [{
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询某个城市的当前天气",
        "parameters": {
          "type": "object",
          "properties": { "city": { "type": "string", "description": "城市名，例如「杭州」" } },
          "required": ["city"]
        }
      }
    }]
  }' | python3 -m json.tool
```

</Callout>

### 真实的响应长这样

```json
{
  "choices": [{
    "finish_reason": "tool_calls",
    "message": {
      "role": "assistant",
      "content": "",
      "tool_calls": [{
        "index": 0,
        "id": "call_00_cSILm8q7Om0JwmpldU8X3988",
        "type": "function",
        "function": {
          "name": "get_weather",
          "arguments": "{\"city\": \"杭州\"}"
        }
      }]
    }
  }],
  "usage": { "prompt_tokens": 281, "..." : "..." }
}
```

## ⚠️ 等等 —— 天气内容呢？

**响应里没有杭州的天气。因为模型根本不知道。**

盯住那个 `"content": ""` —— **它是空的**。模型这一轮**没有回答你的问题**，
它只做了一件事：

> 「我需要调 `get_weather`，参数是 `{"city":"杭州"}`」→ **然后停下来等你。**

杭州今天的天气是**实时数据**，模型的训练数据里没有，它也拿不到。
**它要是直接回答你，那就是编的。**

### 天气出现在第二轮，而且是你喂给它的

```text
第 1 轮   你   → 「杭州天气怎么样？」
          模型 → 「我要调 get_weather(杭州)」      ← content 是空的，停在这里
                 ──────────────────────────────
          ← 你的代码真的去查了，拿到数据
          ← 你把结果喂回去
                 ──────────────────────────────
第 2 轮   模型 → 「杭州现在多云，气温约 18℃，出门带件薄外套」
                 ↑ 这句话里的每个事实都来自【你的工具】，不是来自模型
```

### ★ 一个实验：喂假数据会怎样

我故意编了三组数据喂回去。**模型照单全收：**

| 喂回去的工具结果 | 模型的回答 |
| --- | --- |
| `{"temp":18,"condition":"多云"}` | 杭州现在天气多云，气温大约 18℃…… |
| `{"temp":-50,"condition":"暴雪"}` | 杭州目前的天气是：**暴雪**，气温约 **-50℃** |
| `{"condition":"下刀子"}` | 天气状况：**下刀子** |

**它没有任何办法知道这些是假的。**

第二组它甚至加了句「这数据看起来极端，建议核实」——
但那只是**语言习惯**，它并不是在判断真假，**它无从判断**。

<Callout kind="warn" title="这一节真正要记住的">

**模型是「措辞器」，不是「事实来源」。**

| | 谁负责 |
| --- | --- |
| 认出「这件事要查外部数据」 | **模型** |
| 数据到底是多少 | **工具**（你的代码） |
| 怎么说给人听 | **模型** |

**Agent 的可靠性取决于工具，不取决于模型。**
你以后写 Agent，凡是「事实」必须走工具 —— 绝不能让模型凭记忆答。

</Callout>

## 四个必须注意的点

### ① `arguments` 是**字符串**，不是对象

```text
"arguments": "{\"city\": \"杭州\"}"        ← 字符串！要自己 JSON.parse
```

不是：

```text
"arguments": { "city": "杭州" }             ← 不是这样
```

**为什么这么设计？** 因为流式下这个字符串是**分片下发**的，模型一片一片往外吐：

```text
{"na   →   me":   →   "Ada"   →   }
```

服务端只能给你拼接后的字符串。所以你的代码里必然有一步 `JSON.parse`。

### ② `content` 可能是**空字符串**

模型决定调工具时，`content` 是 `""`，不是 `null`。
你渲染的时候要注意别给用户显示一个空气泡。

### ③ `prompt_tokens` 从 10 变成了 281

因为你刚把**整个工具定义**发过去了。工具描述本身要花 token ——
这是「工具不是免费的」第一次直观体现。工具多了，这笔开销会很可观。

### ④ 还差一步：把结果喂回去

模型只是**要求**调用，它不会自己执行。你得：

1. 执行工具
2. 把结果发回去，**再来一轮**

## 完整的往返

<Callout kind="do" title="第二轮：把结果回填">

第一轮的 `assistant` 消息要**原样塞回去**（连同 `tool_calls`），
然后追加一条 `role: "tool"` 的消息：

```json
[
  { "role": "user", "content": "杭州现在天气怎么样？" },
  {
    "role": "assistant",
    "content": "",
    "tool_calls": [{ "id": "call_00_cSILm...", "type": "function", "function": { "..." : "..." } }]
  },
  {
    "role": "tool",
    "tool_call_id": "call_00_cSILm...",
    "content": "{\"city\":\"杭州\",\"temp\":18,\"condition\":\"多云\"}"
  }
]
```

第二轮回来：

```text
finish_reason : stop
content       : 杭州现在多云，气温约 18°C，体感比较舒适，出门带件薄外套就够啦。
usage         : hit=128  miss=216        ← 注意这里！
```

</Callout>

### `hit=128` 是什么意思

第二轮**缓存命中了 128 个 token**。因为第二轮和第一轮共享同一段前缀
（system + 第一条用户消息 + 工具定义）—— **同样的前缀不用重新算**。

这是「前缀稳定能省钱」的第一次真实体现，下一节会专门做实验。

## ⚠️ 最容易写错的一处：`tool_call_id`

服务端**强制校验**这个 id。它不是建议，是硬约束。

我替你探过三种写错的报错原文（这类错误是 400，**不消耗 token**）：

<Callout kind="warn" title="写错 tool_call_id 会怎样">

**① `role:"tool"` 但前面没有 `tool_calls`**

```text
HTTP 400
Messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

**② `tool_call_id` 和 `tool_calls[].id` 不匹配**

```text
HTTP 400
An assistant message with 'tool_calls' must be followed by tool messages responding
to each 'tool_call_id', The following tool_call_ids did not have response messages: call_WRONG_id
```

**③ 匹配正确** → HTTP 200

</Callout>

**结论**：`tool_call_id` 必须从模型返回的 `tool_calls[].id` **原样透传**，
**不能自己重新生成**。

这条看起来是废话，但它是 Agent 实现里最高频的错误 ——
尤其是当你的工具要并发执行、结果异步回来的时候，
「哪个结果对应哪个调用」就靠这个 id 串起来。

<Callout kind="good" title="本地练，免费">

`npm run mock` 复刻了**一模一样**的 400 校验。
你可以把 id 故意写错，看它返回和真 API 相同的报错：

```bash

npm run mock      # 终端 A
# 终端 B 跑你自己的实现，故意写错 id
```

</Callout>

## 原理：工具调用的完整往返

工具调用不是模型直接执行函数，而是一个五步的协议：

```text
① 你声明 tools（name、description、parameters 用 JSON Schema 描述）
② 模型判断要不要调用，输出 tool_calls：函数名 + 参数（参数是 JSON 字符串）
③ 你的代码解析、校验参数，执行真实的函数
④ 把结果作为 role 为 tool、带上 tool_call_id 的消息放回上下文
⑤ 模型基于结果生成最终回答（或者再次调用工具）
```

第 ⑤ 步可能又回到 ②，这就是 Agent 循环（第 3 章）的雏形。

## 原理：tools 是输入，不是开关

tools 里的 name、description、parameters，会被放进模型的输入上下文，成为 prompt 的一部分。这有两个推论：

- **工具定义占 token，每次请求都要付钱。** 第 0004 节的实验里，同一段对话加上 tools，`prompt_tokens` 从 1778 涨到 2018，多了 240 个。工具越多，每次请求的基础成本越高。
- **模型选工具，靠的是文字描述。** 模型看的是 name、description，以及参数的说明。描述含糊，选错的概率就高。后面讲工具协议的章节会回到这一点。

## 原理：模型输出的是请求，不是动作

`tool_calls` 里是函数名和一段 JSON 字符串形式的参数。它只是一份请求。执行发生在你的代码里，这带来三件事：

1. **参数不可信。** `arguments` 是字符串，可能不是合法 JSON，也可能不符合 schema。解析和校验必须在你这边做。
2. **执行可控。** 你可以做权限检查、参数白名单、审批、超时和审计。
3. **结果也占 token。** 工具结果以 `tool` 消息放回上下文，它同样计入输入。结果太长会挤占上下文，所以要设预算。书的第 36 章讨论的「工具结果预算」就是这个问题，这里只借概念。

## 原理：并行调用

一次回复里，`tool_calls` 是数组，模型可能要求同时调用多个工具。你要逐个执行，并且逐个带回结果，用 `tool_call_id` 一一对应。漏掉任何一个，下一轮请求就会因为缺少对应结果而报错。这是「最容易写错的一处」。

## 原理：安全边界

执行放在客户端，模型就无法直接动你的系统。这是 Agent 安全的起点：后面的权限门、审批和沙箱，都建立在这个边界上。第 11 章的 Harness 运行时会系统地讲。书的第 24 章（策略治理）和第 25 章（安全执行）可以作为这个边界的延伸阅读，这里只借概念。

## 面试映射

| 面试会问 | 这一节给你的答案 |
| --- | --- |
| 模型是怎么决定调用工具的？ | 训练得到的行为，加上你提供的工具描述。它只输出调用意图，不执行。 |
| 工具为什么不让模型直接执行？ | 安全和边界。执行放在客户端，才能做权限、审批和审计。 |
| 一次回复里有多个工具调用怎么办？ | `tool_calls` 是数组，逐个执行，结果按 `tool_call_id` 一一对应地带回去。 |
| 工具参数不合法怎么办？ | 不要直接执行。解析或校验失败，就把错误作为工具结果返回，让模型修正。 |

| 检查 | 说明 |

### ★ 出错时它会直接告诉你病因

我在文件里挂了一个诊断处理器。你把 `tool_call_id` 写错，看到的是这个：

```text
  ❌ 请求失败

      An assistant message with 'tool_calls' must be followed by tool messages
      responding to each 'tool_call_id', The following tool_call_ids did not
      have response messages: call_WRONG

  💡 病因：tool_call_id 和上一轮 tool_calls[].id 对不上。
     ★ 必须原样透传 call.id，不能自己重新生成。
```

**不是一堆堆栈，是病因。** 而且这个诊断认得出三种最常见的错：id 对不上、忘了塞回 assistant 消息、key 没读到。

`arguments` 按你 schema 里 `required` 的字段生成占位值。
