# 护栏：<br/>循环会卡死，而且卡死时很贵

<Lede>上一节的循环「直到模型说停」。如果模型永远不说停呢？这一节给循环加上限，并且让它在停下时能说清楚为什么。</Lede>

## 循环会以三种方式失控

**① 不收敛。** 模型一直要工具，永远不给答案。你写的 `while` 会跑到进程被杀。

**② 原地打转。** 模型每次调同一个工具、传同样的参数，拿到同样的结果，然后再调一次。看起来在动，其实一点进展都没有。

**③ 越跑越贵。** 每一轮都要把历史整段重发。按我们实测的增量（第 1 轮 275、第 2 轮 332，每轮多 57 个 token）估算累计输入：

| 轮数 | 累计输入 token（估算） |
| --- | --- |
| 2 | ≈ 607 |
| 5 | ≈ 1,945 |
| 10 | ≈ 5,315 |
| 20 | ≈ 16,330 |

**20 轮的输入是 2 轮的 27 倍**，而这还只是一次请求。如果用户排队，账单是按这个倍数放的。

## 实测：两个护栏各自拦住什么

练习 06 的自检里有两项专门验这个（我们跑出来的结果）：

```text
✅ 卡死时由「最大步数」兜住  —  steps=4 stopReason=max-steps
✅ 同样的调用重复出现就停    —  steps=2 stopReason=repeated
```

两个数字说明了分工：

- **最大步数**：跑到第 4 步强制停（`maxSteps=4`）。
- **重复检测**：第 2 步就发现「和上一步一模一样」，不用等到 4。

后者更早、更便宜。两个都要有：重复检测抓不住「参数一直在变但没进展」的情况，最大步数抓不住「第二步就在原地打转」。

## 护栏一：最大步数

最简单也最必要的一道。写法就是在循环条件上加一个计数：

```ts
let steps = 0
while (steps < maxSteps) {
  steps++
  // ...每一轮
}
```

**上限设多少？** 取决于任务。我们的建议是「正常任务的最坏情况再留一点余量」：

- 单工具问答：3–5 步足够（正常人 2 步就完了）。
- 多步检索：10–15 步。
- 研究类长任务：20–30 步，但必须同时配成本上限。

超过上限不是错误，是**一个需要告诉用户的正常结局**——见最后一节。

## 护栏二：重复调用检测

判据很简单：**工具名 + 原始参数（字符串原样）** 拼成一个 key，和上一步比。

```ts
const key = `${call.function.name}:${call.function.arguments}`
if (key === lastKey) {
  return { stopReason: 'repeated' }
}
lastKey = key
```

三个细节：

- **用原始的 arguments 字符串比，不要用解析后的对象**。对象比较要深比较，字符串比较就是一行。
- **只和上一步比就够**。连续两次相同基本可以判定在打转；要更严可以保留最近 N 步的集合。
- **检测到重复时不要再执行工具**。第二次执行同样的调用只会浪费钱，还可能重复副作用。

## 护栏三：成本上限（这一节不实现）

除了步数，还有一条常被忽略的线：**累计 token**。

一轮跑下来，把每轮的 `usage.total_tokens` 加起来，超过预算就停。它在步数之外多一层保护，因为「10 步」在不同的提示长度下差别可能几十倍。

第 9 章做评测时会实现它。这一节你只要知道它存在。

## 为什么要把「为什么停」返回给上层

看我们练习里的返回类型：

```ts
export type StopReason = 'done' | 'max-steps' | 'repeated'
export type RunResult = {
  answer: string
  steps: number
  toolCalls: number
  stopReason: StopReason
}
```

`stopReason` 不是给你自己看的，是给**界面**看的：

| stopReason | 界面上该说什么 |
| --- | --- |
| `done` | 正常展示答案 |
| `max-steps` | 「这个任务太复杂，我停下了。要不要我再试一次 / 缩小范围？」 |
| `repeated` | 「我发现自己在重复同一个操作，停下了。」并展示那一步的调用 |

如果你只返回一个空答案，用户看到的就是「什么都没发生」——比报错还糟。

## 你的产出

```bash
npm run mock        # 终端 1

```

自检里两项对应这一节：

- `卡死时由「最大步数」兜住`：用 `?loop=1&vary=1`（每次参数不同，专门绕开重复检测）验证 `maxSteps` 生效。
- `同样的调用重复出现就停`：用 `?loop=1`（每次参数相同）验证第 2 步就停。

这两项一起过，说明你的两道闸是真分开的，不是一个凑数的。

## 面试映射

| 面试会问 | 这一节给你的答案 |
| --- | --- |
| Agent 怎么防止死循环？ | 至少两道：最大步数、重复调用检测（工具名 + 原始参数）。再加成本上限更好。 |
| 为什么要用原始参数比较而不是对象？ | 字符串比较是一行代码，对象要深比较；而且原始字符串就是模型给出的东西，不会因为解析归一化而漏判。 |
| 停下之后怎么告诉用户？ | 返回一个 stopReason 枚举，界面按它给不同的提示。只返回空答案等于什么都没说。 |
