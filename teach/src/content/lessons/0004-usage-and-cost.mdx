# 读懂账单：<br/>为什么改一个字，成本翻 50 倍

<Lede>这一节你会亲手做一个实验，然后看到一个反直觉的结果：<b>改一个字符，缓存命中率从 86% 掉到 0%</b>。</Lede>

## 为什么成本是工程问题

前两节你已经见过这两个字段：

```text
prompt_cache_hit_tokens    ← 命中缓存的部分
prompt_cache_miss_tokens   ← 没命中的部分
```

它们的**价格差 50 倍**：

| | 命中 | 未命中 |
| --- | --- | --- |
| deepseek-flash（低峰） | **$0.003** / 1M | **$0.15** / 1M |
| deepseek-v4-pro（低峰） | **$0.022** / 1M | **$0.66** / 1M |

*（单位：美元 / 百万 token。高峰时段价格翻倍。）*

所以「能不能命中」不是优化项，是**量级差异**。

> 面试会问：「一天一百万次请求大概多少钱？」
> 答不出量级的人，会显得没做过真实系统。

## 动手：自己跑一遍

<Callout kind="do" title="把这段存成 lab/exercises/01-raw-api/cache-probe.ts">

```ts
const BASE = process.env.DEEPSEEK_BASE_URL ?? 'https://api.deepseek.com'
const KEY = process.env.DEEPSEEK_API_KEY!
const H = { 'Content-Type': 'application/json', Authorization: `Bearer ${KEY}` }

// 造一段长且稳定的前缀
const LONG = '以下是项目背景资料，请阅读后回答问题。\n' +
  Array.from({ length: 40 }, (_, i) =>
    `第 ${i + 1} 条：本系统采用 TypeScript 编写，模块 ${i + 1} 负责数据校验与错误分类。`
  ).join('\n')

async function call(label: string, system: string) {
  const r = await fetch(`${BASE}/chat/completions`, {
    method: 'POST', headers: H,
    body: JSON.stringify({
      model: 'deepseek-flash',
      thinking: { type: 'disabled' },
      max_tokens: 5,
      messages: [{ role: 'system', content: system }, { role: 'user', content: '一句话总结。' }],
    }),
  })
  const u = (await r.json()).usage
  const pct = Math.round((u.prompt_cache_hit_tokens / u.prompt_tokens) * 100)
  console.log(`${label.padEnd(24)} prompt=${u.prompt_tokens}  hit=${u.prompt_cache_hit_tokens}  miss=${u.prompt_cache_miss_tokens}  ${pct}%`)
}

await call('第 1 次', LONG)
await call('第 2 次', LONG)
await call('第 3 次', LONG)
await call('system 改一个字', LONG.replace('以下是', '下面是'))
```

### 你会看到（我跑过的真实结果）

```text
第 1 次                  prompt= 1778  hit=    0  miss= 1778    0%
第 2 次                  prompt= 1778  hit= 1536  miss=  242   86%
第 3 次                  prompt= 1778  hit= 1536  miss=  242   86%
system 改一个字            prompt= 1778  hit=    0  miss= 1778    0%
```

**盯住最后一行。** prompt 长度一模一样（1778），只改了一个词 ——
**命中率从 86% 直接掉到 0%。**

按 flash 的价算这笔账：

| | 命中 | 未命中 | 这一次的成本 |
| --- | --- | --- | --- |
| 已缓存 | 1536 | 242 | ≈ $0.000041 |
| 改一个字之后 | 0 | 1778 | ≈ $0.000267 |

**差了 6.5 倍。** 而且在真实系统里，这个前缀可能是几千甚至几万 token 的
system prompt + 工具定义 + 检索到的文档。

## 从数据能读出什么

### ① 缓存是**按前缀单元**整块命中的

第二次的 `hit=1536`，不是「一部分一部分累积」，而是**整块** ——
而且第三次仍然是 1536，不会继续涨。

说明存在一个**单元的边界**（这里正好落在 system 消息的位置）。
这个边界是服务端划的，不是你控制的。

### ② 改在哪儿，就失效在哪儿

`system 改一个字 → hit=0`。

这解释了一条工程实践：**把稳定的东西放前面，把变化的东西放后面。**
system prompt、工具定义、少变的背景资料放最前；用户这次的问题放最后。

### ③ 但我不能从一次实验就断定机制

上面是**观察**。服务端怎么划分单元、有没有延迟、多长时间过期 ——
**这些都不是我能从三个数据点推出来的。**

我做 P1 调研时第一次设计这个实验就**设计错了**：我以为缓存有 TTL 参数可以直接测，
查了官方文档才发现根本没有这个参数。

<Callout kind="warn" title="这一节真正想教你的东西">

**不要从观察直接跳到机制。**

`hit=1536` 是个观察。你可以在工程上**利用**它（把稳定内容放前面），
但要说「缓存是按 XX 规则划分的」，你需要更硬的证据。

这个区分在面试里很关键 —— 面试官会追问「你怎么知道的」。
答「我做了个实验，结果是……但机制我不确定」比编一套解释**分数高得多**。

</Callout>

## 就这样省下钱

三个立刻能用的做法：

| 做法 | 为什么 |
| --- | --- |
| **system prompt 和工具定义放最前，且保持字节级稳定** | 它们是最大的一块前缀；改一个字全部作废 |
| **不要往 system 里塞时间戳、随机 id、请求序号** | 最隐蔽的缓存杀手 —— 看起来无害，实际每次都让前缀全废 |
| **多轮对话天然友好** | 每一轮都在上一轮末尾追加，前缀天然稳定（见下方实验） |

## 附：另外两个实验（你可以自己跑）

我也测了这两个，结果可能和你猜的不一样：

```text
═══ 工具定义会不会破坏缓存 ═══
① 无 tools              prompt= 1778  hit= 1536   86%
③ 加上 tools            prompt= 2018  hit= 1664   82%   ← prompt 涨了，hit 也涨了
⑤ 去掉 tools，回到①      prompt= 1778  hit= 1536   86%

═══ 把新消息插在【中间】 ═══
① 基准                  hit= 1536   86%
② 末尾追加               hit= 1536   86%   ← 不变
③ 插到 system 之后        hit= 1536   86%   ← 也不变！
```

③ 那条尤其反直觉：**把一条新消息插在 system 后面，system 的缓存居然还在。**

所以「改动任何位置都会失效」这句话我说得太满了 ——
**失效的是被改动所在的那个单元**。system 是一个单元，改它才失效；动它后面的不影响它。

**这就是「先做实验，再下结论」的价值**：我第一版的结论是错的。

## 原理：计费的结构

输入分两部分：命中缓存的 token（hit）和未命中的 token（miss）。输出单独计费。第 0004 节的价目表里，`deepseek-flash` 低峰时命中是 $0.003 / 1M，未命中是 $0.15 / 1M，相差 50 倍。高峰时段价格翻倍（以官网为准，价格会变）。

成本可以写成：

`成本 = 命中 token 数 × 命中单价 + 未命中 token 数 × 未命中单价 + 输出 token 数 × 输出单价`

下面只算输入部分，因为输出价格不在这张表里。

## 原理：一个 Agent 循环的成本例子

假设一个 Agent 跑 20 轮。第 k 轮的输入是 3000 + 500k 个 token（历史越来越长），每轮的输入都以上一轮的输入为前缀。

- **没有缓存**：20 轮的输入合计 155000 个 token，全部按未命中计费：155000 × $0.15 / 1M = $0.02325。
- **有缓存**：每轮的前缀（即上一轮的全部输入）都命中，只有新增的 500 个 token 未命中。第 0 轮的 3000 个未命中。合计命中 142500 个，未命中 12500 个：142500 × $0.003 / 1M + 12500 × $0.15 / 1M ≈ $0.0023。

缓存让输入成本降到原来的约 10%。这个结论依赖三个假设：前缀完全不变、缓存没有过期、价格没有变。任何一个不成立，结论都要重新算。

## 原理：缓存是怎么命中的

- **前缀匹配**：服务端从第一个 token 开始逐个比较，直到第一个不同的位置。之前的部分命中，之后的全部未命中。
- **所以稳定前缀是第一原则**：system prompt、工具定义、固定规则放在最前面，每轮都保持不变；动态内容放在后面。第 0004 节的实验已经演示了「改在哪儿，就失效在哪儿」。
- **书的第 39 章「Prompt Cache 稳定性」**把这一点展开成工程规则：缓存只认第一个差异之前的部分，稳定内容和易变内容要按位置分开。这是那本书的工程总结，我们这里只借概念，实现要自己写。
- **缓存有存活时间**，具体多久以官方文档为准，不要写死在代码里。

## 原理：输入和输出要分开算

缓存只优化输入部分。如果输出很长，即使输入全部命中，成本也可能主要在输出。所以估算要先拆开：输入多少、命中多少、输出多少。书的第 23 章「Token 预算控制」讨论的是预算的工程实现：三级预算、用量记账、背压和熔断。

## 面试映射

| 面试会问 | 这一节给你的答案 |
| --- | --- |
| 怎么降低大模型应用的成本？ | 缩短输入，稳定前缀提高缓存命中，限制输出长度，按任务选模型。 |
| 为什么输出 token 比输入贵？ | 输出是逐个生成的，每个输出 token 都要读取前面全部的 KV（第 1 章）。 |
| 为什么把动态内容放在 system prompt 最前面，会让缓存全部失效？ | 它改变了整段前缀，之后的内容都无法命中。 |
| 怎么估算一个 Agent 循环的成本？ | 按轮拆分输入，算出每轮的命中和未命中，再加上输出。不要只算最后一轮。 |
