# KV Cache 与显存：<br/>一次长上下文要占多少显存

<Lede>第 0005 节说，decode 每生成一个 token 都要读取之前所有的 K 和 V。这些 K 和 V 放在哪里，占多少？这一节算给你看。</Lede>

## 为什么需要 KV Cache

注意力计算里，每个 token 都要和它前面的所有 token 做计算。生成第 t 个 token 时，需要前面 t−1 个 token 的 K 和 V。

如果每一步都重算所有历史 token 的 K 和 V，decode 的计算量会随长度越来越大。KV cache 的做法很简单：**每个 token 只算一次 K 和 V，存下来，之后每一步只追加一组新的。**

```text
生成第 1 个字：算 K₁ V₁，存下来
生成第 2 个字：读 K₁ V₁，算 K₂ V₂，存下来
生成第 3 个字：读 K₁ V₁ K₂ V₂，算 K₃ V₃，存下来
……
```

代价是显存。缓存的东西会随上下文长度线性增长。

## 原理：Q、K、V 到底是什么

前面直接用了 K 和 V，这里补上它们是什么。

注意力可以想成一次**软查找**。普通的键值数据库是精确匹配：给一个 key，取回对应的 value。注意力不精确匹配，它先算「有多像」，再按相似度把 value 混起来。

三个角色：

| 角色 | 全名 | 它代表什么 | 类比 |
| --- | --- | --- | --- |
| Q | Query（查询） | 当前 token 想找什么信息 | 你输入的关键词 |
| K | Key（键） | 每个 token 能被怎么找到 | 每条记录的索引 |
| V | Value（值） | 被找到之后贡献什么内容 | 每条记录的内容 |

它们不是三种不同的东西，而是**同一个向量乘三组不同的权重矩阵**得到的三份表示。设第 l 层、第 t 个 token 在这一层的输入向量是 h（维度 d），那么：

- q = h · W_Q
- k = h · W_K
- v = h · W_V

W_Q、W_K、W_V 是训练出来的权重，同一层里所有 token 共用。然后算这个 token 的输出：

1. 用它的 q 去和前面每个 token 的 k 做点积，得到一串分数（越像分越高）。
2. 分数先除以 √d_k，再 softmax，变成一组加起来等于 1 的权重。
3. 用这些权重，把前面所有 token 的 v 加权求和。

一句话：**用我的 query 去比对你的 key，按相似度取你的 value。**

## 原理：什么叫「注意力头」

前面那个 `q = h · W_Q` 只描述了**一个头**。实际上每一层里有几十组**独立**的 `W_Q`、`W_K`、`W_V`，每一组叫一个「头」（head）。

```text
一层 = 32 个并行的头（Llama-2-7B）

第 1 个头：用 W_Q1、W_K1、W_V1 → 算一组注意力 → 输出 128 维向量
第 2 个头：用 W_Q2、W_K2、W_V2 → 算一组注意力 → 输出 128 维向量
…
第 32 个头：…
                  ↓ 拼起来
        32 × 128 = 4096 维
                  ↓ 乘 W_O
              投影回 4096 维
```

每个头都独立做一遍「我的 query 比对你的 key，取你的 value」，互不干扰；结果拼接后再乘一个输出投影 `W_O` 合回隐藏维度。

### 为什么不全用一个头

一次注意力只能产生**一组**权重，一个头只能给每个位置算出一个加权平均。如果想让模型同时关注不同的事（「上一个名词是什么」和「这里是不是句末」），一个头不够。

拆成多个头，就有了多个并行的「视角」，每个头学出自己的关注模式，最后拼起来。每个头具体学了什么，属于可解释性研究，本课不展开。

### 为什么拆成 32 个头，计算量几乎不变

- 单个头满维度（4096）的投影：`4096 × 4096`
- 32 个头，每个 `4096 × 128`：`32 × 4096 × 128 = 4096 × 4096`

一样大。所以「多头」不是把计算量乘以 32，而是**在总计算量不变的前提下，把同一份计算分成多个独立的子空间**。这通常写成 `head_dim = hidden_size / num_heads`（Llama-2-7B：4096 ÷ 32 = 128）。

注意：不是所有模型都守这条。DeepSeek-V3 用 MLA，隐藏维度 7168、128 个头，但每个头的维度是 `qk_nope_head_dim` 128 + `qk_rope_head_dim` 64 = 192，并不等于 7168 ÷ 128 = 56。MLA 不按这个惯例。

### 这就是「查询头数」和「KV 头数」会不同的原因

- **MHA**：32 个查询头和 32 个 KV 头一一对应，每个头各存一份 K、V。
- **GQA**：查询头还是 32 个，但 K/V 只存 8 份，每 4 个查询头共用一份。

所以 KV cache 的大小取决于 **KV 头数**，不是查询头数。

## 原理：为什么能缓存 K 和 V，却不缓存 Q

这是 KV cache 成立的根本原因，值得单独说一句。

- **k 和 v 只由 h 和固定的权重决定。** 一个 token 被处理过之后，它的 h 就定了，k 和 v 也再不会变。所以可以存下来反复用。
- **q 不用缓存。** 每一步只需要「当前新生成的那个 token」的 query，历史 token 的 query 用完就丢。

还有一个容易漏掉的点：**每一层都有自己的 K 和 V**。61 层就是 61 份，显存要按层数乘上去 —— 这就是公式里那个「层数」的来源。

## 公式：从最小的一块开始乘

这个公式看着吓人，其实就是四层乘法。从最小的一块开始，一层层往上乘。用的是 Llama-2-7B 量级的配置：32 层、32 个注意力头、`head_dim` 128、bf16。

### ① 一个头、一个 token

一个注意力头里，K 是一个 `head_dim` 长的向量，V 也是。`head_dim` 就是一个头里向量的长度，这里是 128。

```text
一个头：K 128 个数 + V 128 个数 = 256 个数
bf16 每个数 2 字节 → 2 × 128 × 2 = 512 字节
```

### ② 加上头数：一个 token、一层

Llama-2-7B 有 32 个注意力头，标准多头（MHA）里每个头都有自己独立的 K 和 V。

```text
32 个头 × 512 字节 = 16 KiB     ← 一个 token 在一层里的 K、V
```

换个算法更直观：32 个头 × 128 维 = **4096 个数**，正好等于模型的隐藏维度（`hidden_size` = 4096）。所以**一层的 K 就是 4096 个数，一层的 V 也是 4096 个数** —— K/V 的宽度等于隐藏维度。`2 × 4096 × 2 = 16 KiB`，结果一样。

### ③ 加上层数：一个 token

32 层，每层各存各的，互不共用。

```text
16 KiB × 32 层 = 512 KiB         ← 一个 token 的 KV cache
```

这就是表里「每 token 512 KiB」的来源，也是练习 03 自检的第一个数字。

### ④ 加上上下文和 batch：一个请求、一批请求

```text
一个请求，4K 上下文：512 KiB × 4096 = 2 GiB
整批 16 个请求：    2 GiB × 16 = 32 GiB
```

### 为什么这个数字值得关心

7B 模型的权重是 7B × 2 字节 = 14 GB，约 13 GiB。

- 单个请求、4K 上下文：KV cache 2 GiB ≈ 权重的 15%。
- **16 个并发请求、4K 上下文：32 GiB ≈ 权重的 2.5 倍。**

显存不是被模型权重吃掉的，是被 KV cache 吃掉的 —— 这就是为什么推理服务要先算「能同时开几个请求」，而不是只看模型多大。

### 回头看那个公式

```text
每 token 字节数 = 2 × 层数 × KV 头数 × head_dim × 每元素字节数
                ↑                                ↑
          K 和 V 各存一份                   fp16 / bf16 都是 2 字节
```

| 因子 | 它是什么 | 上例中的值 |
| --- | --- | --- |
| 2 | K 和 V 各一份 | 2 |
| 层数 | 每层各存各的，不共用 | 32 |
| KV 头数 | 有几个头在存 K/V | 32（MHA）/ 8（GQA） |
| head_dim | 每个头里向量多长 | 128 |
| 每元素字节数 | 精度决定 | 2（bf16） |

上下文 token 数和 batch 大小是另外两个乘数，不在「每 token」这个口径里 —— 这就是为什么全量公式要多乘 `token 数 × batch 大小`。

## GQA 省在哪

GQA（grouped-query attention）不减少查询头，只减少 **KV 头数**：

- 32 个查询头照常计算，表达力基本不变。
- 但 K/V 只存 8 份，每份被 4 个查询头共享（32 ÷ 8 = 4）。

```text
MHA：32 个 KV 头 → 512 KiB/token
GQA： 8 个 KV 头 → 128 KiB/token     ← 正好四分之一
```

表里那两行的差别，就只是这一个数字从 32 变成 8。4K 上下文时 2 GiB → 512 MiB，batch 16 时 32 GiB → 8 GiB。

## MLA：DeepSeek 怎么省

DeepSeek-V3 的官方配置（我们在它的 `config.json` 里核对过）：

- `num_hidden_layers`：61
- `num_attention_heads`：128
- `kv_lora_rank`：512
- `qk_rope_head_dim`：64
- `torch_dtype`：bfloat16

MLA 不存完整的 K 和 V。它把 K、V 压缩成一个低维的 latent（维度 512），再额外存一小部分带 RoPE 的 key（维度 64）。因此每个 token、每一层只存：

512 + 64 = 576 个数

换算：576 × 2 字节 × 61 层 = 70,272 字节，约 68.6 KiB/token。一个 128K 的单序列，约占 8.58 GiB（bf16）。

作为对照，假设把同样的维度换成标准多头（128 个头，K 维 192，V 维 128）：每 token 约 4.77 MiB，128K 上下文约 610 GiB。两者相差约 71 倍。

<Callout kind="warn" title="对照的口径">

「假想的标准多头」只用来说明量级。DeepSeek-V3 实际不是这样存的。读这个对照时，请把它当成「如果不压缩，会贵到什么程度」的思想实验。

</Callout>

推理时，MLA 会把 latent 投影回各个头的 K 和 V 再计算。具体的矩阵吸收技巧，这一节不展开。

## ★ 和第 0004 节的 prompt cache 不是一回事

这两个概念很容易被混为一谈。面试官问「KV cache 是什么」，如果你答成「就是 prompt cache」，会被继续追问到底。

| 维度 | prompt cache（第 0004 节） | KV cache（本节） |
| --- | --- | --- |
| 在哪里 | 服务端，跨请求 | 单次请求，占 GPU 显存 |
| 缓存的是什么 | 一段前缀的计算结果，可被后续请求复用 | 每一层的 K 和 V，供本次生成复用 |
| 解决什么问题 | 重复前缀的计费，以及 prefill 的成本 | 生成时不必重算历史 token |
| 生命周期 | 由服务端决定，我们没有测过 TTL | 请求结束就释放 |

## 显存决定了你能跑多长

一张卡的显存，主要放三样东西：模型权重、KV cache、其他开销。长上下文和大 batch 都会放大 KV cache。

同一个标准多头模型，单个 4K 序列占 2 GiB。如果 batch 是 16，就是 32 GiB。这就是为什么长上下文服务要花那么多钱，也是为什么 MLA 和 GQA 这类设计有价值。

## 原理：显存预算不只有 KV

推理时的显存大致由四部分组成：

| 部分 | 大致由什么决定 |
| --- | --- |
| 权重 | 参数量 × 精度（7B @bf16 ≈ 13 GiB） |
| KV cache | 上面的公式：随上下文和 batch 线性增长 |
| 激活 | 中间张量，和 batch、序列长度有关，通常远小于前两项 |
| 框架开销 | 推理引擎自己的缓冲区、图、临时空间 |

前两项是主要的。权重是固定的，KV cache 是随负载变的 —— 所以「能同时服务多少请求」由 KV cache 决定，而「能不能装下这个模型」由权重决定。

## 原理：四种注意力，同一个问题的四种解法

| 方式 | 每个 token 每层存多少 | 特点 |
| --- | --- | --- |
| MHA（多头注意力） | 每个头各一组 K、V | 表达力最强，KV cache 最大 |
| MQA | 所有查询头共享一组 K、V | KV cache 最小，但表达力下降明显 |
| GQA | 查询头分组，每组共享一组 K、V | MHA 和 MQA 之间的折中 |
| MLA（DeepSeek-V2 提出） | 一个低维的 latent 向量，加一小段位置分量 | 压缩存储，计算时再还原 |

以 DeepSeek-V3 为例（官方配置，我们核对过）：MLA 的 `kv_lora_rank` 是 512，`qk_rope_head_dim` 是 64。每个 token 每层存 512 + 64 = 576 个值；61 层，bf16 每个 2 字节，合计 61 × 576 × 2 = 70272 字节，约 68.6 KiB。作为对照，同样规模的模型如果是标准多头（128 个头，K 维 192、V 维 128），每个 token 约 4.77 MiB，是 MLA 的约 71 倍。这个对照只说明量级，不是 DeepSeek-V3 的真实存法。

## 原理：PagedAttention —— 怎么放

KV cache 的大小已经难办，放法更难。每个请求的长度不同，而且还在增长。如果连续预留最大长度，大部分会浪费（内部碎片）；如果按需分配，又会留下零散的空洞（外部碎片）。

PagedAttention 借鉴了操作系统的分页：把 KV cache 切成固定大小的块，用块表记录逻辑位置到物理块的映射。块不需要连续，碎片大幅减少。同样的机制还能用来共享块，比如并行采样和 beam search。论文报告了相对基线的吞吐提升，具体数字以论文为准，我们没有复现。

## 原理：两种优化的关系

MLA 减少的是每个 token 要存的数量；PagedAttention 解决的是存放的效率。两者解决的问题不同，原则上可以叠加，具体取决于推理框架的支持。

## 原理：精度直接改变显存

前面的公式里有个「每元素字节数」。它由精度决定：

| 精度 | 每元素字节 | 对 KV cache 的影响 |
| --- | --- | --- |
| fp32 | 4 | 最占显存，推理几乎不用 |
| bf16 / fp16 | 2 | 常见默认值，本课的算例用的就是它 |
| fp8 | 1 | 理论上一半，但精度损失要评估 |

DeepSeek-V3 的官方配置里 `torch_dtype` 是 `bfloat16`，所以我们按 2 字节算。如果推理框架支持把 KV cache 单独存成 fp8，同样的显存能装下两倍的上下文。代价是还原时的精度损失，具体掉多少要看任务，我们没有测。

这也是为什么「显存够不够」这个问题不能只问模型参数量：精度、KV cache 的存法、batch 大小，三个变量一起决定。

## 原理：MoE 让「总参数」和「每 token 计算量」分开

DeepSeek-V3 是混合专家模型（MoE）。官方 config 里写着：61 层，256 个路由专家，每个 token 激活 8 个（另外还有 1 个共享专家）。技术报告的摘要原话是：

> 671B total parameters with 37B activated for each token.

这句话对成本结构有两个直接含义：

- **权重显存按 671B 估**，因为所有专家都得加载进显存。
- **每个 token 的计算量按 37B 估**，因为一次只走 8 个专家。

所以它能用相对便宜的单 token 成本，提供接近更大稠密模型的质量。这是 MoE 被普遍采用的原因。但它也带来新的工程问题：专家分布不均会导致某些卡忙、某些卡闲，这是推理框架要处理的，本课不展开。
